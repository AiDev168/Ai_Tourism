# Rahgard — راهنمای تولید دیکشنری کامل دیتابیس و جدول‌ها

**واقعیت فعلی:** نسخه V2 روی VPS از PostgreSQL 17 و volume `rahgard_staging_pgdata` استفاده می‌کند. گزارش انتشار ۲۲ migration تا `0023` را تأیید کرده است. در آخرین گزارش عملیاتی، سازمان‌ها/خدمات/پیشنهادها/مقصدهای منتشرشده ۰ بودند. این فایل بدون اتصال به سرور نمی‌تواند تعداد واقعی تمام دیتابیس‌ها یا ستون‌های تمامی جدول‌ها را تأیید کند.

## خروجی مورد نیاز

برای **هر دیتابیس دسترس‌پذیر** یک پوشه جدا، و برای هر جدول یا view یک فایل Markdown مستقل تولید می‌شود:

```text
docs/database/live-schema/
  manifest.json
  README.md
  <database-name-hash>/
    <schema-name-hash>/
      tables/<table-name-hash>.md
      views/<view-name-hash>.md
```

در هر فایل: هدف جدول، فهرست تک‌تک ستون‌ها، **نوع دقیق** PostgreSQL (شامل `numeric(p,s)` و `varchar(n)`)، nullable، پیش‌فرض ایمن، فرمت پایه، توضیح کاربردی (اگر در COMMENT یا فرهنگ واژه‌ها موجود باشد)، PK/FK/Unique/Check، Index، RLS و Policy. **هیچ سطری از دیتابیس، متن گفتگو یا اطلاعات کاربری خوانده یا منتشر نمی‌شود.**

## اجرای فقط‌خواندنی

۱. در یک محیط مجاز اپراتور با دسترسی فقط‌خواندنی `psycopg` نسخه ۳ را نصب/استفاده کنید؛ بهتر است از محیط موجود Backend استفاده شود. هیچ DSN یا پسوردی داخل Git یا خروجی فرمان وارد نشود.

۲. اطلاعات اتصال صرفاً از متغیر محیطی خصوصی `RAHGARD_SCHEMA_DSN` خوانده می‌شود. آن را از Secret Store موجود اپراتور مقداردهی کنید. برای تمام دیتابیس‌های **قابل اتصال با آن نقش**:

```bash
python tools/schema/rahgard_schema_documenter.py \
  --all-accessible-databases \
  --descriptions-json docs/database/field_descriptions.json \
  --output-root docs/database/live-schema
```

یا برای اتصال فقط به DB فعلی `rahgard_pilot_vps_staging` (نام باید در محیط واقعی بررسی شود):

```bash
python tools/schema/rahgard_schema_documenter.py \
  --database rahgard_pilot_vps_staging \
  --descriptions-json docs/database/field_descriptions.json \
  --output-root docs/database/live-schema
```

۳. خروجی `manifest.json` باید وضعیت دیتابیس‌های غیرقابل‌دسترسی را هم ذکر کند. `complete=true` تنها پوشش متادیتای دیتابیس‌های **واقعاً متصل‌شده** را بیان می‌کند؛ **به معنی تکمیل توضیح کسب‌وکاری همه فیلدها نیست**.

۴. توسعه‌دهنده باید معنای ستون‌های فاقد COMMENT/Glossary را با SQL Migration، مدل‌های Pydantic، React Form و منطق سرویس تطبیق دهد. هیچ حدسی را به عنوان حقیقت منتشر نکند. هر فیلد باید معنای پارامتر، واحد، قالب ورودی/خروجی، validation، حساسیت و نقش مجاز را بگیرد. `field_descriptions.json` نقطهٔ شروع مبتنی بر بخش‌هایی از کد بررسی‌شده است، نه دیکشنری کامل.

۵. پس از تکمیل دیکشنری و ممیزی محرمانگی، مستندات را در GitHub Commit/Push کنید و manifest را در CI با اسکیمای مهاجرتی بازتولید و تفاوت‌ها (drift) را گزارش دهید. اتصال مستقیم تولید برای **مقایسه متادیتا** باید فقط خواندنی باشد.

## نکات امنیتی/دسترسی

- هر اتصال با تراکنش `READ ONLY`، timeout کوتاه و صرفاً SELECT از `pg_catalog` اجرا می‌شود.
- از سیستم‌دیتابیس‌ها، جدول‌های سشن/OTP و کاربران مقدار واقعی (row data) استخراج نمی‌شود؛ فقط ساختار و قیود ثبت می‌شود.
- تا زمانی که دسترسی سایر دیتابیس‌ها فراهم نباشد، ادعای «تمام دیتابیس‌ها» ممنوع است. در صورت AccessDenied نام DB و نوع خطا باید در Manifest بیاید، نه پسورد/DSN.
- اسم دیتابیس، policy و SQL defaultهای ثابت ممکن است اطلاعات داخلی داشته باشند؛ پیش از Public کردن مخزن/سند بررسی شوند. defaultهای دارای literal متنی به صورت پیش‌فرض مخفی شده‌اند.
- مالک باید دربارهٔ حساسیت نام جدول‌ها، schema و سیاست‌های RLS برای انتشار عمومی تصمیم بگیرد. پیش‌فرض، نگهداری در مخزن **خصوصی پروژه** است.

## معیار تکمیل

- سرشماری مستقل `pg_database` و تعداد schema/table/view در برابر PostgreSQL زنده/backup، با شناسه و زمان قابل ردیابی.
- یک Markdown برای **تمام** جدول‌ها و viewهای هر DB قابل دسترسی، بدون جداول جاافتاده.
- **صفر فیلد با توضیح نامشخص** در نسخه نهایی پس از تکمیل توسط توسعه‌دهنده و بازبینی مالک؛ فیلدهای حساس با توضیح طبقه‌بندی‌شده نه مقدار واقعی.
- تطبیق فهرست FK/unique/RLS/index با اسکیمای زنده و هر migration.
- لینک‌دهی فرم‌های نقش‌محور به API و جدول/فیلدهای معتبر؛ هیچ فرم دستکاری مستقیم metadata/migrations/OTP/session طراحی نشود.
