# راهنمای واقعی ورود و گردش کار شرکت‌ها در Rahgard V2

این راهنما بر پایهٔ مسیرهای فعلی UI/API و مشاهدهٔ فقط‌خواندنی در ۲۴ نوامبر ۲۰۲۶ نوشته شده است. دادهٔ شرکت آزمایشی در پایگاه زنده ایجاد نشده است.

## ورود و ثبت‌نام

1. به `https://hinaa.ir/` بروید و از بخش ورود در نوار بالای صفحه، روش فعال را انتخاب کنید.
2. پاسخ عمومی `GET /api/v1/auth/method` در زمان بررسی این روش‌ها را برگرداند: `otp` و `staging_invite`؛ ثبت‌نام آزمایشی ایمیلی فعال بود. تحویل SMS برابر `unavailable` بود، پس UI نباید ادعا کند پیامک ارسال شده است.
3. برای حساب آزمایشی، مسیر «ایجاد حساب آزمایشی با ایمیل» و سپس ورود ایمیلی قابل استفاده است؛ ایمیل در این محیط تأیید نمی‌شود. روش دعوت نیز فقط با کد دعوتی که اپراتور مجاز جداگانه تحویل می‌دهد قابل استفاده است. کد دعوت را در گزارش یا URL قرار ندهید.
4. پس از ورود، پیوند «فضای کسب‌وکار» در نوار اصلی به مسیر واقعی `/partners` می‌رود. ورود به این مسیر بدون نشست معتبر، فرم ورود را نشان می‌دهد.

## ثبت شرکت و تکمیل اطلاعات

در `/partners`، کاربر واردشده این مراحل را انجام می‌دهد:

1. «ثبت شرکت»: نام حقوقی، نام نمایشی، نوع فعالیت و کد کشور دوحرفی. API `POST /api/v1/partners/organizations` یک سازمان خصوصی با وضعیت اولیهٔ در انتظار و دریافت درخواست غیرفعال ایجاد می‌کند و برای ایجادکننده عضویت owner می‌سازد. ایجاد سازمان آن را تأیید یا منتشر نمی‌کند.
2. «معرفی نخستین خدمت»: نام، شرح کوتاه و نوع خدمت. API `POST /api/v1/partners/organizations/{organization_id}/services` خدمت و متن محلی‌سازی‌شدهٔ آن را ذخیره می‌کند؛ شناسهٔ داخلی خدمت را سرور می‌سازد.
3. جزئیات اختیاری قیمت، زمان‌بندی، اتصال به مقصد منتشرشده، پیشنهاد و مشاهدهٔ دسترسی در بخش بازشوندهٔ «قیمت، زمان و اتصال به مقصد (اختیاری)» قرار دارند. این فرم‌ها APIهای واقعی schedule، service-destination، offer، price و availability را صدا می‌زنند. زمان و قیمت مشاهده‌های تاریخ‌دار هستند؛ خود فرم هیچ واقعیت عملیاتی یا انتشار عمومی را تضمین نمی‌کند.
4. شرکت می‌تواند ارجاع‌های مدرک را برای بررسی ارسال کند. ارسال، وضعیت را خودکار verified یا active نمی‌کند. پروفایل و خدمات تا انتشار/تأیید مجاز خصوصی می‌مانند.

## صف بازبین و تفکیک تصمیم‌ها

مسیر UI جداگانه‌ای برای «مالک محلی» یا مدیریت عمومی جداول وجود ندارد. صف بررسی در همان `/partners` فقط هنگامی رندر می‌شود که درخواست `GET /api/v1/partners/platform/organization-review` با نشست فعلی مجاز باشد؛ API بدون capability، پاسخ 403 می‌دهد. مجوز از `partner.platform_grants` بررسی می‌شود و این جدول CRUD عمومی ندارد.

بازبین مجاز سه تصمیم مستقل و ثبت‌شونده دارد:

1. بررسی مدرک: `POST /api/v1/partners/platform/verification-cases/{case_id}/decision` با verified، needs_information یا rejected و دلیل.
2. پذیرش درخواست: `POST /api/v1/partners/platform/organizations/{organization_id}/application-decision` با approve/reject و دلیل.
3. فعال/غیرفعال‌کردن دریافت درخواست: `POST /api/v1/partners/platform/organizations/{organization_id}/participation-decision` با activate/deactivate/suspend و دلیل.

این تصمیم‌ها مجوز و actor را سمت سرور بررسی می‌کنند و رخداد audit ایجاد می‌کنند. شرکت نمی‌تواند خودش را بررسی یا فعال کند. تغییرات کاربر عادی نیز حق‌عضویت یا وضعیت چرخه‌عمر را تنظیم نمی‌کند.

## اشتراک درخواست مسافر و پیوندهای محافظت‌شده

مسافر فقط سازمان‌هایی را می‌بیند که در `partner.share_eligible_organizations` هستند؛ اشتراک نیازمند انتخاب شرکت و تأیید صریح مسافر است. آمار فقط‌خواندنی زمان تهیه: **۰ مقصد عمومی و ۰ سازمان واجد شرایط اشتراک**. در نتیجه در سایت زنده، نبود گزینهٔ شرکت یک وضعیت دادهٔ واقعی است؛ پذیرنده یا گزینهٔ ساختگی نمایش داده نمی‌شود.

پیوندهای عمیق فقط در UI پس از اشتراک مجاز ساخته می‌شوند و شکل دقیق آن‌ها چنین است:

- `/partners?org={organization_id}&share={share_id}&revision={revision_number}&view=request`
- `/partners?org={organization_id}&share={share_id}&revision={revision_number}&view=itinerary`

شناسه‌ها نمونهٔ placeholder هستند و نباید با مقادیر واقعی در مستند عمومی جایگزین شوند. URL به‌تنهایی مجوز نیست: UI در `/partners` و API صندوق، نشست و عضویت همان سازمان و اعتبار share/revision را دوباره بررسی می‌کنند. لغو اشتراک دسترسی را می‌بندد. اطلاعات اصلی درخواست به‌طور پیش‌فرض اشتراک نمی‌شود؛ فقط با رضایت جداگانهٔ مسافر در snapshot قرار می‌گیرد.

## نقشهٔ UI به API و مجوز

| کار | مسیر/API | نگهداری و دسترسی |
|---|---|---|
| ثبت/فهرست شرکت‌های خود کاربر | `POST/GET /api/v1/partners/organizations` | نشست معتبر، CSRF برای نوشتن؛ RLS و مالکیت سازمان |
| ویرایش مشخصات | `PUT /api/v1/partners/organizations/{id}` | فقط فیلدهای نمایه؛ وضعیت احراز/پذیرش از payload پذیرفته نمی‌شود |
| ارسال برای بررسی | `POST /api/v1/partners/organizations/{id}/verification-cases` | عضو مجاز؛ ارجاع‌های یکتا و محدودشده |
| خدمت | `POST /api/v1/partners/organizations/{id}/services` و `PUT /api/v1/partners/organizations/{id}/services/{service_id}` | عضو سازمان؛ متن در `service_localizations` |
| صفحهٔ بازکردن کار | `GET /api/v1/partners/organizations/{id}/workspace?locale=...` | نشست و دسترسی سازمانی؛ بازخوانی بعد از ذخیره |
| برنامه/پیشنهاد/قیمت/دسترسی | `/schedules`, `/offers`, `/prices`, `/availability` زیر سازمان | CSRF، عضو سازمان، شناسه‌های وابسته اعتبارسنجی‌شده |
| صندوق درخواست | `GET /api/v1/partners/organizations/{id}/requests` | عضویت فعال و سهم معتبر؛ بدون دسترسی cross-tenant |
| پاسخ شرکت | `POST /api/v1/partners/organizations/{id}/requests/{share_id}/responses` | عضویت و درخواست واجد شرایط؛ tenant-scoped |
| تصمیم بازبین | `/platform/...` | capability مشخص؛ ممنوع برای شرکت متقاضی |

CRUD مستقیم SQL برای session، OTP، audit، grantها، migration ledger یا سیاست‌های RLS از این فرم‌ها ارائه نمی‌شود. API فعلی فرم ساخت/ویرایش شعبه ندارد؛ ستون‌های branch فقط در مستند schema ثبت شده‌اند و نباید UI به‌عنوان قابلیت فعال برای آن معرفی کند.

## نتیجهٔ آزمون جداشده

در acceptance مرورگر محلی، با PostgreSQL 17 موقت و حساب‌های fixture: ثبت/ویرایش سازمان، ارسال پرونده، بازبینی مستقل و فعال‌سازی با رخداد audit، خدمت، اتصال مقصد منتشرشده، برنامه، پیشنهاد، قیمت و availability ذخیره و بازخوانی شدند. سازمان دوم دادهٔ سازمان اول را نخواند (workspace خالی) و نوشتن cross-tenant با 403 رد شد. مسافر فقط پس از consent اشتراک ساخت؛ درخواست/نسخه در صندوق شرکت ظاهر شد و پس از احراز هویت جدید، trip و itinerary ذخیره‌شده بازشدند. این نتایج **دادهٔ fixture در DB موقت** هستند، نه ثبت شرکت یا انتشار محتوای زنده.

Migration `0024_partner_review_audit_actions.sql` در همان DB موقت برای اصلاح ثبت audit تصمیم `verification_case` و محدودکردن دسترسی مستقیم app-role به platform grants آزموده شد. Migration 0024 روی VPS اجرا نشده است و دادهٔ زنده تغییر نکرده است.
