# راهنمای دسترسی امن مالک و بازبین راهگرد

## وضعیت فعلی

پنل در نشانی `https://hinaa.ir/admin` قرار دارد. در پیکربندی پایلوتِ ثبت‌شده، ورود مسافر با ثبت‌نام ایمیل/گذرواژهٔ staging یا دعوت ایمیلی و گذرواژه انجام می‌شود؛ تحویل SMS/OTP در حال حاضر در دسترس نیست، پس کد پیامکی را نمی‌توان دریافت کرد. روش واقعی را همیشه از پاسخ عمومی `/api/v1/auth/method` همان انتشار بررسی کنید. دسترسی مدیریتی با ورود عادی ایجاد نمی‌شود؛ اپراتور باید مجوز مشخص را از ابزار کنترل‌شدهٔ سرور اعطا کند. هیچ مسیر ثبت‌نام عمومی برای مدیر وجود ندارد. پس از استقرار نسخهٔ حاوی مهاجرت `0026_platform_reviewer_mfa` و تنظیم امن کلیدهای سرور، تغییرات حساس به TOTP و تأیید کوتاه‌مدتِ همان نشست نیاز دارند. تا آن زمان، پنل فقط‌خواندنی می‌ماند.

در وضعیت بررسی‌شدهٔ فعلی، VPS تا مهاجرت `0023_partner_trip_responses` پیش رفته است؛ مهاجرت‌های `0024` تا `0026` و کلیدهای MFA هنوز برای محیط زنده فعال نشده‌اند. بنابراین این راهنما روش عملیاتیِ نسخهٔ آماده‌شده را توضیح می‌دهد، نه ادعای فعال بودن قابلیت روی سایت زنده.

## اعطای دسترسی

1. کاربر با روش ورود عادیِ فعال در پایلوت وارد شود. ایجاد حساب، دعوت یا OTP به‌تنهایی اختیار مدیریتی نمی‌دهد.
2. اپراتور هویت را خارج از گزارش‌ها و کانال‌های عمومی تطبیق دهد و UUID کاربر را از کنسول مجاز دریافت کند.
3. ابتدا ابزار `backend/scripts/provision_platform_capability.py` را بدون `--apply` اجرا و خروجی `DRY_RUN` را بررسی کند. ابزار اتصال را فقط از `RAHGARD_OPERATOR_DATABASE_URL` و نشانگر پایگاه داده را از `RAHGARD_PILOT_DATABASE_MARKER` می‌خواند؛ مقدار این متغیرها را در خروجی یا Issue ننویسید.
4. فقط پس از تأیید اپراتور مجاز، همان فرمان با `--apply` و تأیید عملیاتی `RAHGARD_OPERATOR_GRANT_CONFIRM=APPLY_APPROVED_PLATFORM_GRANT` اجرا شود. دلیل باید دقیق و حداقل ۱۰ نویسه باشد. اعطای نخستین مجوز `admin_overview_read` فقط از کنسول اپراتوری محافظت‌شده و با هویت اپراتور جدا از کاربر هدف ممکن است.

الگوی فرمان (شناسه‌ها را فقط در نشست خصوصی اپراتور جایگزین کنید):

```powershell
uv run python backend/scripts/provision_platform_capability.py --target-user <UUID> --operator-user <UUID> --capability admin_overview_read --action grant --reason "Owner access approved by operator"
$env:RAHGARD_OPERATOR_GRANT_CONFIRM = 'APPLY_APPROVED_PLATFORM_GRANT'
uv run python backend/scripts/provision_platform_capability.py --target-user <UUID> --operator-user <UUID> --capability admin_overview_read --action grant --reason "Owner access approved by operator" --apply
Remove-Item Env:RAHGARD_OPERATOR_GRANT_CONFIRM
```

مجوزها را بر اساس وظیفه و جداگانه بدهید: `admin_overview_read` برای نماهای تجمیعی، `organization_review` برای بررسی شرکت، `candidate_review` و `source_review` برای بازبینی نامزد و منبع، و `catalogue_publish` برای انتشار. از اعطای همهٔ مجوزها به یک حساب خودداری کنید. خودتأییدی شرکت مجاز نیست.

## راه‌اندازی TOTP و تأیید نشست

پس از ورود مجاز و استقرار تنظیمات MFA:

1. در بالای `/admin` بخش «تأیید دومرحله‌ای مدیر» را باز کنید و «راه‌اندازی برنامهٔ کدساز» را بزنید.
2. کلید یک‌بارنمایش‌داده‌شده را در برنامهٔ TOTP مورداعتماد ثبت کنید. پاسخ‌های ثبت کلید و کدهای بازیابی `no-store` هستند؛ از تصویر، ضبط صفحه، گزارش مرورگر، چت یا لاگ استفاده نکنید.
3. کد شش‌رقمی برنامه را وارد کنید. پس از موفقیت، کدهای بازیابی یک‌بار نمایش داده می‌شوند؛ آنها را در محل امن و جدا از سرور نگه دارید.
4. برای تصمیم مدیریتی، یک کد تازه وارد کنید. اعتبار تأیید حداکثر پنج دقیقه و فقط برای همان نشست ورود است. کد TOTP تکراری رد می‌شود.

کلید `PLATFORM_ADMIN_MFA_ENCRYPTION_KEY_HEX` باید ۶۴ رقم هگزادسیمال (۳۲ بایت) و `PLATFORM_ADMIN_RECOVERY_PEPPER` حداقل ۳۲ بایت باشد. هر دو باید از مدیر رازهای سرور و مستقل از PostgreSQL به برنامه تزریق شوند. مهاجرت یا راه‌اندازی برنامه نباید این مقادیر را بسازد، چاپ کند یا در Git ثبت کند. اگر کلید گم شود، رازهای ذخیره‌شده قابل رمزگشایی نیستند؛ پیش از تغییر یا چرخش کلید، فرایند نگهداری و بازیابی مصوب لازم است.

## تزریق فایل‌محور برای سرور (آماده است؛ هنوز روی VPS فعال نشده)

نسخهٔ فعلی برنامه می‌تواند این دو مقدار را از فایل محافظت‌شده بخواند:

- `PLATFORM_ADMIN_MFA_ENCRYPTION_KEY_FILE`
- `PLATFORM_ADMIN_RECOVERY_PEPPER_FILE`

در Compose، overlay اختیاری `deploy/staging/compose.platform-admin-mfa.yaml` دایرکتوری اختصاصی `RAHGARD_ADMIN_SECRET_DIR` را فقط‌خواندنی به `/run/rahgard-admin-secrets` متصل می‌کند. آن directory فقط secretهای admin را نگه دارد، `0700` و owner آن UID برنامه (10001 در image فعلی) باشد. فایل‌ها regular، بدون symlink و mode `0400` یا `0600` هستند تا validator بتواند دسترسی را بررسی کند.

هر دو فایل را **فقط از مسیر secret manager** بسازید؛ مقدارها را در shell argv، خروجی ترمینال، history، فایل `.env`، log، CI یا issue ننویسید. پس از بررسی file ownership/mode و `docker compose ... config --quiet`، restart فقط در پنجرهٔ تغییر مجاز انجام شود. سپس health check غیرحساس فقط وضعیت `configured/disabled` را از `Settings` نشان دهد؛ مقدار یا طول secret چاپ نشود. در این task فایل‌های live ساخته/چرخانده نشدند و overlay روی VPS اجرا نشد.

مراحل کامل backup/restore، rehearsal ۰۰۲۴–۰۰۲۶، مرزبندی clone زنده/ایزوله و محدودیت portability در [راهنمای بازیابی Issue 27](RAHGARD_ISSUE27_RECOVERY_GUIDE_FA.md) آمده است. Grant مالک و reviewer همچنان از ابزار operator جدا provision می‌شود؛ MFA enrollment از UI فقط بعد از grant انجام می‌شود.

## بازیابی و لغو

- کد بازیابی فقط یک‌بار قابل استفاده است و یک تأیید پنج‌دقیقه‌ای برای همان نشست ایجاد می‌کند. سپس گزینهٔ «بازنشانی کدساز با نشست تأییدشده» را انتخاب و TOTP را دوباره ثبت کنید.
- رخدادهای شروع ثبت، فعال‌سازی، TOTP، بازیابی و بازنشانی در جدول ممیزی محافظت‌شده ثبت می‌شوند؛ راز TOTP و خود کدهای بازیابی ثبت نمی‌شوند.
- برای لغو مجوز از همان ابزار اپراتوری با `--action revoke` استفاده کنید. با لغو آخرین مجوز مدیریتی، وضعیت MFA و تأییدهای وابسته نیز پاک می‌شوند؛ رخداد اعطا/لغو در دفتر ممیزی باقی می‌ماند.
- اگر نه برنامه و نه کد بازیابی در دسترس است، اپراتورِ مستقل پس از احراز هویت کاربر باید مجوز را لغو و در صورت لزوم دوباره اعطا کند. هیچ مسیر عمومیِ دورزدن MFA وجود ندارد.

مدیریت تنظیمات ارائه‌دهندهٔ هوش مصنوعی همچنان فقط برای پایلوت محلی مجاز است و این راهنما آن را در محیط عمومی فعال نمی‌کند. پیش از استقرار زنده، مهاجرت‌های ۰۰۲۴ تا ۰۰۲۶، بازیابی پشتیبان، کلیدهای MFA، و روش ورود باید جداگانه و با گیت عملیاتی تأیید و تمرین شوند.
