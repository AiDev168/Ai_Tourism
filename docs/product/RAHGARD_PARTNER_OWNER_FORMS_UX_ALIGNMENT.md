# Rahgard V2 — قواعد سازگاری فرم‌ها با پوستهٔ اصلی و ساده‌سازی واقعی کار

**وضعیت:** قرارداد طراحی برای ادغام در محصول؛ فایل HTML همراه صرفاً پیش‌نمایش آفلاین است و نباید به‌عنوان یک اپلیکیشن دوم Deploy شود.

## الزامات قطعی

1. از ساختار و کلاس‌های موجود `frontend/src/partners/PartnerWorkspace.tsx`، `frontend/src/styles.css`، Auth و APIهای V2 استفاده شود. کامپوننت‌ها **داخل فریم اصلی Rahgard** افزوده شوند؛ هدر، ناوبری، فونت و Theme مستقل دوم ایجاد نشود.
2. هماهنگی بصری: خانواده فونت `Estedad Variable` با fallback موجود، `html[data-rahgard-theme]`، رنگ‌بندی بنفش/سرمه‌ای تیره و روشن موجود، شعاع گوشه‌ها، فاصله‌ها، کنترل‌های فرم و کنترل کنتراست فعلی. مقدارهای نمایش در نمونه HTML فقط برای تطبیق تقریبی هستند؛ منبع قطعی CSS پروژه است.
3. «ساده» یعنی **حداقل تصمیم و حداقل کلیک** برای کاربر، نه ظاهر خلوت ولی گردش کار پیچیده: در ابتدا فقط نام شرکت/نوع/کشور؛ سپس معرفی یک خدمت؛ سپس قیمت، زمان و درخواست‌ها در صورت نیاز.
4. شناسه‌های UUID، `organization_id`, `service_key`، نام جدول، RLS و JSON نباید ورودی اجباری کاربر عادی باشند. رابطه‌ها از انتخاب‌گرهای جست‌وجویی با داده مجاز API و شناسهٔ داخلی سرور تولید شوند.
5. قبل از داشتن شرکت یا خدمت، فرم‌های نامربوط غیرفعال و **دلیل** واضح نشان داده شود. هر مرحله دارای عنوان، کمک کوتاه، ذخیرهٔ پیش‌نویس، بازکردن مجدد، اصلاح خطای همان فیلد و پیام موفقیت قابل اعتماد باشد.
6. انتخاب‌های ثابت و enumهای واقعی از Backend خوانده شوند. پیش‌نمایش از برچسب‌های فارسی صرفاً نمایشی استفاده می‌کند و مجوز اختراع مقدار جدید برای DB/API نیست.
7. بخش‌های حرفه‌ای مانند شناسه داخلی، تکرار زمان‌بندی، تنظیم ظرفیت و چندزبانه تنها زیر «تنظیمات بیشتر» و برحسب نیاز نمایش داده شوند. مقدار پیش‌فرض هر فیلد باید بر اساس قرارداد معتبر سرور تعیین شود؛ فرم آن را حدس نزند.
8. تقویم جلالی در UI فارسی، ISO در API، پول با واحد/مقیاس شفاف، جلوگیری از تبدیل ضمنی تومان/ریال/میلیون، مسیر درست پیام‌های خطا، RTL کامل، عرض موبایل 390 و دسکتاپ 1440؛ رنگ متن و زمینه در تمام وضعیت‌ها WCAG AA.
9. هیچ شرکت تازه‌ثبت‌شده خودکار `verified` یا `active` نشود؛ مالک و بازبین مستقل، مدارک و درخواست را در صف مجاز بررسی کنند؛ مالک شرکت نتواند وضعیت خودش را تأیید کند.
10. صندوق و لینک‌های شرکت تحت **نشست معتبر و عضویت سازمانی** هستند؛ URL به تنهایی دسترسی نیست. برای صفر شرکت واجد شرایط، مسافر پیام روشن ببیند نه دکمهٔ بی‌اثر.
11. حوزه مدیریت جداول: جدول‌های کسب‌وکاری فقط با فرم نقش‌محور مبتنی بر API؛ audit، OTP، session، secrets، migration ledger، RLS فقط مشاهدهٔ محدود و ابزار عملیاتی جدا، نه CRUD عمومی.
12. از ایجاد دومین Planner، Backend، پنل شبیه‌سازی‌شدهٔ دائمی یا جدول‌های تکراری جلوگیری شود. Preview آفلاین در تولید mount نشود.

## آزمون‌های UX الزامی

- کاربر جدید بدون دانستن اصطلاحات دیتابیس، زیر ۳ مرحلهٔ اصلی بتواند یک شرکت و خدمت ثبت کند؛ فیلدهای ضروری بیش از حد قرارداد واقعی نباشند.
- کاربر با صفر شرکت، صفر درخواست، دادهٔ ناقص، اعتبار منقضی و خطای سرور سردرگم یا گیر نکند؛ مسیر بازگشت/اصلاح معلوم باشد.
- هم حالت روشن و هم تاریک روی فرم، modal، placeholder، خطا، دکمه و focus با CSS محاسبه‌شده تست شوند.
- روی 390px بدون اسکرول افقی، ناوبری قابل دسترسی و کادرها درون فریم Rahgard دیده شوند.
- پاسخ شرکت‌ها و فرم‌ها مجوزها و tenant isolation را حفظ کنند؛ هیچ تغییر Schema یا فعال‌سازی خارج از مسیر review انجام نشود.
